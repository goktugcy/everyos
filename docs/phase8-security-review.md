# Phase 8 security review

Internal implementation review, 2026-10-11. This is not an independent penetration test.

## Boundaries reviewed

- The API remains unprivileged. `release.status`, `release.check` and `release.install` have strict
  protocol schemas, permissions, timeouts and production policy checks. Installation requires a
  user actor; neither the browser nor CLI supplies commands, scripts, URLs or a trust key.
- API routes validate strict bodies/queries, enforce roles and check the administrator's password.
  The safety archive must be local, verified, created by the same administrator within 30 minutes,
  include the database and all account homes, and be pinned before the root job starts.
- Release sources, keys, packages, transactions and snapshots live under recursively checked
  root-owned paths. Configuration cannot be edited by the API account. Offline sources reject
  symlinks; HTTPS rejects private/reserved destinations and pins the checked DNS result through TLS.
  Redirect destinations are explicitly restricted. Downloads have byte and time limits.
- Ed25519 signatures cover exact manifest bytes. Version, architecture, package identity, size,
  SHA-256, expiry, minimum upgrade version and schema version are checked before installation.
  Expired signatures are accepted only for already cached recovery artifacts.
- The independent systemd worker re-verifies the previous package before downtime. Offline SQLite
  snapshots and durable transactions recover both binaries and database after failed migrations or
  a killed worker. File data and relevant directory entries are fsynced before advancing state.
  Maintenance blocks ordinary API mutations and delays background schedulers until verification.
- API audit records the authorized request. Structured root journal events and a private fsynced
  append-only audit file preserve final outcomes across database recovery. Passwords, keys and
  subprocess output are excluded. CLI credentials use hidden prompts or stdin, never argv.
- The ordinary APT path rejects EveryOS selection, excludes it from bulk upgrades and pins the
  installed version against dependency-driven replacement. All EveryOS systemd units and the
  private app-config mount are protected from general service-management operations.
- The API unit runs as `everyos` with an empty capability set, `NoNewPrivileges`, read-only system,
  private devices/tmp and protected home/kernel paths. Root agent/updater policies retain the host
  access required for their typed operations. App configs use a real private host tmpfs so Docker
  can read bind sources. Removal/purge acts only on EveryOS resources and preserves owner data.

## Findings resolved during disposable-host validation

Package archives now include parent directories. `libatomic1` is a declared runtime dependency.
The generated agent key uses the expected base64url encoding. API-owned data is not recursively
chowned on upgrades. Configuration uses the production environment variable. Recovery artifacts
are verified before services stop; interrupted downloads cannot enter dpkg. Schema verification
and snapshot restoration prevent an old binary from starting against a failed newer migration.
The queue is serialized, and a restarted worker resumes the recorded transaction. Update progress
survives service restarts; transient browser connection errors clear when the API returns.

## Validation and operational limits

Exact command results and disposable-host scenarios are in
[phase8-acceptance.json](phase8-acceptance.json). Test releases use an ephemeral key and intentionally
broken packages; they are never production releases. Existing owner services and containers were
not used for destructive tests.

Publisher signing is a root trust boundary: protect the release environment and distribute the
public key independently. Production signing secrets and a live signed publication are owner
configuration, not generated by these tests. Key rotation requires an explicit recovery-cache
transition; changing a key must not invalidate the only cached recovery release.

Release migrations currently modify only the EveryOS SQLite database. Homes, wallpapers and
container data remain outside that migration contract. A release that changes external data
formats needs a separately designed recovery path. Additional file-manager roots and backup
disks require deliberate systemd drop-ins; configuration does not override the unit sandbox.
